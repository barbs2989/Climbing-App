# Maintainability audit — where the code is hard to work on, and what was done

Owner note, 2026-11-25: *"Audit maintenance of the app where we have confusing and code that is too long and
difficult to maintain when things go wrong."* This file is the audit's measurement, its decisions, and the
runbook it produced. Re-measure before trusting a number here: main moves every few minutes.

## When something breaks: where to look first

| Symptom | First move |
|---|---|
| A climber saw "This screen hit a bug", or anything threw on a phone | `npm run errors:read` — every error filed to `app_errors` in the last 7 days, grouped, each minified frame mapped back to `file:line:column in function` with the code at that column (hidden source maps, kept 90 days as the deploy artifact `sourcemaps-<entry script>`). A stack copied from anywhere else: `npm run errors:read -- --stack "<stack>" --build index-XXXX.js` |
| The live site does not show what was merged | `npm run check:drift` |
| A screen shows nothing, or "you have none" | it is usually a failed read shown as empty: `docs/guards/outage-and-read-failures.md` |
| One section of a page is blank but the rest works | `lib/SectionErrorBoundary.jsx` caught it — the error is in `app_errors` too |
| A guard went red and you do not know why it exists | `grep -rn "check:NAME" docs/guards/` — every guard has an entry saying why, and what it cannot see |
| Where does feature X live? | `CURRENT_STATE.md` → `docs/features/<area>.md` (files, tables, symbols — kept true by `check:feature-docs`) |
| Which file holds a component that used to be in ClimbMatchCore? | `src/components/<Name>.tsx`, registered in `MOVED` in `scripts/lib/guard-sources.mjs` |

## Findings, and what was done about each

1. **A crash report named nothing anyone could open.** `app_errors` stored the minified stack
   (`index-x.js:1:482113`) and no source maps existed, so the position mapped to nothing — and the source it
   would map to has 40,000-character lines, so even a line number is not enough without the column.
   **Fixed (#3987):** hidden source maps, kept off the site and uploaded per build; `npm run errors:read`
   prints file, line, column, function and the code at the column.

2. **Dead one-off scripts drowned every search.** Of 3,151 files in `scripts/oneoff/`, 1,743 were named by no
   live file (repo, memory notes, session reports), including transitively (named only by other dead files).
   Every `grep` for a column, table or function returned these finished runs first.
   **Removed (PR "Remove 733 dead one-off files"): 715 files (2.7 MB) from `scripts/oneoff/` and 18 from `enrichment-wip/`**, under rules
   chosen to keep anything that could still be needed:
   - not named — by basename — in any tracked file, any memory note, or any note-session report;
   - not touched in the last 7 days (a parallel session may be mid-run);
   - not a backup, rollback, "before" snapshot or undo file (history of production writes stays readable in place);
   - not in a subdirectory whose name a live file mentions (a script reading `dir/` by `readdirSync` names the
     directory, not each file);
   - not matching a directory scan a guard runs (`inject-*`, `apply-trip-plans-*`, `link-multi-approach-batch*.plan.json`).
   Every one stays in git history: `git log --all --oneline -- scripts/oneoff/<name>` finds it,
   `git show <sha>^:scripts/oneoff/<name>` restores it.
   The other ~1,000 dead `oneoff` files are backups or inside directories a live file names; they were left.
   **Decided:** no new rule or guard forbids new one-offs. They are how production data work is recorded, and
   `scripts/oneoff/` is already excluded from the guards that would make them expensive.

3. **`lib/db.js` is one 8,080-line file** holding every read and write the app makes, 416 exports, across ~30
   unrelated domains (routes, crews, groups, messages, review desk, data-rights…), separated only by comment
   banners. **Split (#4011):** 18 flat files `lib/db-<domain>.js` (120–820 lines each, each headed by what it
   holds), generated by `scripts/oneoff/split-db-by-domain.mjs` so every line landed in exactly one file;
   `lib/db.js` re-exports the same 417 names, so no app import changed. To find a function:
   `grep -n "function NAME" lib/db-*.js`. Guards read the joined text through `readDbSource()`
   (docs/guards/infrastructure.md). Flat, not `lib/db/`, because every `lib/` walker reads `lib/` without
   recursing. One-off probes written before the split that read `lib/db.js` by path in a spelling other than
   `readFileSync(path.join(ROOT, "lib/db.js"))` now see only the re-export list; the 24 that used that
   spelling were repointed, the ~20 others are finished runs and were left — use `readDbSource()` if one is rerun.

4. **`ClimbMatch.jsx` / `ClimbMatchCore.jsx` lines up to 40,000 characters.** The dense one-line-per-declaration
   style is a recorded convention (CLAUDE.md) and ~135 build guards match the source TEXT with regexes keyed to
   it; reformatting would blind or break them wholesale. **Decided: not reformatted.** What made long lines
   *dangerous* — a crash you cannot locate in them — is fixed by finding 1 (the column, and the code at it).
   The component extraction (docs/refactor-progress.md) already moved 273 components out; App's remaining
   bulk is 298 `useState` hooks and their handlers.

5. **Already in place, verified still working, no change:** `AppErrorBoundary` + per-section
   `SectionErrorBoundary`, so a bug blanks one section, not the app; `lib/errorReport.js` filing to
   `app_errors`; `check:types` (strict TS over `src/`) and `lint` at zero findings with no baseline; a notes
   entry for every guard in `docs/guards/`; feature docs held true by `check:feature-docs`.

## Watch list (not split, on purpose)

The component-extraction series stopped by decision on 2026-10-30 (docs/refactor-progress.md): a file is
split further only when a change to it is hard **because of its size**. Nothing in this audit showed that, so
these stay as they are and are the first candidates when it does: `src/components/SuggestFix.tsx` (156 KB, one
component), `lib/PartnerSearch.jsx` (113 KB), `lib/CrewCard.jsx` (102 KB). `ClimbMatch.jsx`'s remaining bulk
is App's 298 `useState` hooks and their handlers; moving them into custom hooks is a different refactor, and
the guards that read App's text would each need the treatment `lib/db.js` got.

## Once the app is live: keeping it running (audit 2026-11-26)

Owner note, 2026-11-26: *"Audit the maintenance of this whole app. Will it be easy? Audit where we can make
it easier to maintain once the app goes live."* The 2026-11-25 pass above was about the CODE. This one is
about OPERATING it: noticing breakage, keeping dependencies current, and recovering data.

**Short answer: the code is well guarded, and noticing that something broke was the weak link.**
~138 guards run on every PR in about 3 minutes (median of the last 10 green `build` runs: 2-3 min), every
guard has a notes entry, and crashes on phones map to `file:line` (`npm run errors:read`). But on the day
of this audit:

| What | Measured 2026-11-26 | Done |
|---|---|---|
| Red checks went unnoticed for days | render-guards red on main 3 days, `audit:silent-reverts` red on every merge for a day, the nightly offline files 3 nights, `check:counts` 5 days. Each workflow emails separately, nothing says how long a check has been red | **`npm run ops:status`** prints every workflow's state on main and since when. **`.github/workflows/ops-status.yml`** keeps ONE GitHub issue labelled `ops-status`: opened when something goes red (a notification), commented on only when the set of red checks changes, closed when main is green |
| Scheduled checks run far less often than their crons say | in 72 h: deploy-drift 7 of 144 promised runs, live-site-check 6 of 12, zero-state and render-guards 6 of 18; daily jobs ran but ~10 h late. GitHub sheds scheduled runs under load | ops-status is triggered by **other workflows finishing** (`workflow_run`), which is not shed; `ops:status` prints each cron's real run rate. Fast detection of a DOWN site needs an outside monitor, which is an owner to-do (below) |
| render-guards red on main (#3876 + 0525/0527) | the CI fixture relocked its crew's day to "yesterday" on every run; since 0527 a crew's day cannot move for 14 days after it arrives, so every run died | `scripts/lib/durable-fixture.mjs`: the trip crew keeps its day while its recap is open and moves only once the database allows; a second durable crew with no agreed day carries the Crews-tab card and chat assertions |
| `audit:silent-reverts` red on every merge | #4007 deliberately removed #3908's Help-fill exports without naming them | entry added to `REVIEWED` |
| Every Dependabot PR showed a red check, so none was merged | GitHub gives a Dependabot PR no Actions secrets; `check:zero` saw no database, walked seed data, failed | `zero-state.yml` skips with a warning on a Dependabot PR that has no database secret (anywhere else a missing secret still fails). Adding the Dependabot secrets is an owner to-do; once they exist the walk runs on those PRs again |
| Major upgrades pile up | open 8+ days: vite-plugin-react 4→6, eslint 9→10, babel 7→8 (vite 6→8, TypeScript 5→7, React 18→19 offered before) | **Decided: left open, not ignored.** Ignoring majors in dependabot.yml would hide them entirely (and an ignore rule can also hold back a security fix in that range); a major upgrade is a deliberate piece of work, done one package per PR. `ops:status` lists them with their age so they cannot be forgotten |
| No backup or restore procedure written down anywhere | Supabase: the FREE plan has no automatic backups; Pro keeps daily backups for 7 days; point-in-time recovery is a paid add-on (~$100/month per 7 days). Daily backups do not include Storage objects (photos) | owner to-do (below); the 2026-10-25 cascade delete is the incident this would have undone |

### The routine, once live

- **Daily (1 minute):** is the `ops-status` issue open? If it is, it names the red workflow and links its last run. `npm run ops:status` prints the same locally.
- **Weekly:** `npm run errors:read` (crashes on phones, grouped); merge the grouped Dependabot minor/patch PR once `build` is green; glance at the Supabase dashboard's Database report (Disk IO budget has been exhausted by bulk jobs before).
- **Per major upgrade:** one PR per package, read its migration guide, run `lint` + `type-check` + the guards that read what it touches.
- **Before any bulk data job:** the throttle rules in CLAUDE.md, and a rollback JSON first.
